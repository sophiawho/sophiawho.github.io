Embedded Bank Widgets — Link vs Pay-by-Bank

One prep for two interview questions · companion to plaid_link_frontend.html and pay_by_bank_widget.html

Roughly 70% of either answer is the same design. Learn the shared spine cold, then learn three root differences and let everything else cascade from them. Do not study these as two problems.

1. How to use this document

There are two files in this folder that each design one system end to end. This one exists for the failure mode where you have studied both separately and then freeze in the room because you cannot remember which detail belongs to which.

The structure to hold in your head is short.

  • A shared spine. Embedding, isolation, OAuth, the nonce, who owns flow state. Identical in both, and it is most of the answer.
  • Three root differences. Everything that diverges traces back to one of them. If you can name the root, you can derive the consequence live instead of memorizing it.
  • A disambiguation script. Four questions in the first three minutes that tell you which problem you are actually in.
The trap. Because the front halves are near-identical, it is easy to spend twenty minutes on the shared part and run out of clock before reaching whatever actually distinguishes the problem you were given. Get through the spine briskly and confidently, then spend your depth on the delta.

2. The shared spine

Every row here is true of both systems, with the same reasoning and often the same words. This is what you should be able to say without thinking.

ConcernHow both do it, and why
Embedding A small JS SDK on the host page injects an iframe served from the provider's origin. Same-origin policy is the isolation boundary, and it works in both directions. The host cannot read the widget's DOM or its token, and the widget cannot read the host's page.
Host channel postMessage for lifecycle events. Pin the exact target origin on send, check event.origin against an allowlist on receive, with exact string equality. Never includes, because host.com.attacker.io passes that.
Who owns flow state The server. The client renders whatever step the server reports and never asserts a step itself. Illegal transitions are rejected, not ignored. No optimistic advance.
Creation The customer's backend creates the session using a server-held API secret. The browser can never create one. This is identical in both, and Link's version is easy to forget because most diagrams omit the arrow.
Browser credential One short-lived, narrowly scoped bearer token handed down to the iframe. link_token or session_token. Safe in a browser because of what it cannot do, not because it is hidden.
Bank leg OAuth. The bank cannot be framed, since every real bank sends X-Frame-Options: DENY or frame-ancestors 'self', and credential entry in a third-party iframe is the phishing pattern anyway. So the bank must occupy a top-level browsing context.
Redirect method The redirect back from the bank is always a GET. That is the OAuth spec plus browser behavior on a 302. You do not choose the method, so your callback design has to accommodate it.
CSRF A server-generated, session-bound, single-use nonce on the redirect. Burned with one atomic conditional UPDATE … WHERE used_at IS NULL, asserting one row affected, before the code exchange. A client-generated nonce is worthless.
Code exchange The provider's client secret at the bank buys the access token, server to server. The nonce plays no part in this and is never sent to the token endpoint.
Access token Never touches a browser, in either system. Envelope-encrypted under a KMS on the provider's backend.
Rehydration A full redirect destroys the SPA. Two independent recovery paths, a sessionStorage breadcrumb for the same-tab case and the nonce in the URL for the empty-storage or new-tab case. Both systems need this, because both need a mobile path.
Institution search Typeahead over a few thousand rows, identical for every user, cacheable at the CDN. The only genuinely read-heavy endpoint, and in both systems it is the least interesting part. Say so and move on.
Mobile Popups unreliable, app-to-app deep links into the bank's native app, return via universal link. Which is why recovery should key off the server-side nonce lookup rather than client storage.
Edge cases Every state has an error edge. Bank down, nonce mismatch, session expired, user cancels. Rate-limit session creation and OAuth attempts per token, per IP, per customer. Monitor nonce-failure spikes as forged-callback probing.
The line that covers half the security questions in either interview. Credentials live only between the user's browser and the bank. Neither we nor the customer ever see them. Say it early and unprompted.

3. The three root differences

Everything that diverges traces to one of these. Learn the roots, derive the rest.

Root 1 — Money moves, so the flow does not end when the user leaves

Link's deliverable is ready in seconds, while the user is still watching. Pay-by-bank's real answer arrives one to three days later, long after the tab is closed.

Cascades into. An async state machine with a real gap between authorized and succeeded · settlement webhooks as a load-bearing integration · transactional outbox · at-least-once delivery with retry ladders · a cursor endpoint for missed events · a reconciliation sweeper · a ledger · ACH return codes and who eats them.

Root 2 — The deliverable is a state, not a credential

This is the sharpest one and the one most people miss.

  • Link's terminal event is a token handoff. public_token goes to the browser, up to the customer's backend, then a server-to-server exchange for the access_token. The entire three-step gradient exists because a credential has to reach a third party through an untrusted channel.
  • Pay-by-bank has no public_token equivalent. No credential is handed to the merchant at all. They get a signed webhook and a GET endpoint. Their integration surface is dramatically smaller. The bank OAuth exchange still happens, it just stays entirely inside our backend.

Also cascades into. An amount exists, which is entirely new attack surface. Idempotency now matters at the money layer, not just at session creation. Risk scoring and underwriting become central rather than absent.

Root 3 — The context is a live checkout

Destroying the host page costs a cart, a half-filled address form, a promo code, and all the merchant's JS state. On an onboarding or settings screen that is annoying. At checkout it is a conversion disaster.

Be precise about what kind of difference this is. It is a UX and conversion cost, not a security difference. Both are equally secure, because the bank ends up top-level either way. And you still build the full-redirect rehydration path for mobile, so you do not get to delete Link's hardest deep dive. You are choosing a default, not removing work.

4. The token gradients, side by side

Keep the two chains apart, because merging them is the easiest mistake to make here. Both systems run chain A. The bank issues an authorization code, and the provider exchanges it with its own client_secret for a bank token that never leaves the provider's servers. Nothing in chain B ever "becomes" that token. The nonce gates the exchange but is not an input to it.
Why chain B is the difference to lead with. Its length tells you the shape of the whole back half of the design. Three means there is a handoff, so you need an exchange endpoint, a customer-side integration step, and a story about what happens if the middle token leaks. One means the answer is delivered asynchronously instead, so you need webhooks, an outbox, and a reconciliation path.

One more distinction worth having ready. In Link, the thing the customer ends up holding is Plaid's own access_token, a handle to the Item. The bank's OAuth token stays inside Plaid. So even in the three-token case, the customer never touches a bank credential. That invariant holds in both systems, and it is the cleanest way to state the trust model.

6. Two corrections worth internalizing

Access token TTL follows scope, not product type

It is tempting to say "Link's token is long-lived and pay-by-bank's is short." True in the table above, but it is a consequence of a scope decision, not a property of the product.

The real axis is does the product need access after the user leaves.

  • Link exists for ongoing account access, so long TTL.
  • Our pay-by-bank token is short only because we scoped out repeat payments. Add stored mandates and it becomes long-lived, and you inherit a PaymentMethod object and merchant-initiated debits with no widget in the flow at all.

State it as the axis, not the fact. The axis survives a follow-up question. The fact does not.

There are two redirect URIs, and people conflate them

The bank-facing one must belong to the provider. Not a style choice. It is registered once with each bank, and if every customer registered their own, onboarding one merchant would mean thousands of bank registrations. One provider URI scales, per-customer does not.

The customer-facing one is the hop home after a full redirect blew away the host page. Link has you host a page and re-initialize with the received URI. Our pay-by-bank design uses a pre-validated return_url stored on the session.

The good line. "The bank-facing redirect URI has to be mine, one registration per bank. Whether there is a second hop back to the customer depends entirely on whether I destroyed their page, which is why the popup removes an entire integration step for them."

7. API shape, which applies to both

Both systems expose a customer-backend-to-provider API authenticated with a server secret. The question of what protocol comes up in either interview.

The axis is not "is it server to server." That tells you nothing. The axis is do you control the client. You do not. Your callers are on PHP 7, Ruby, a Shopify app, Java 8, and someone's Node script.

REST at the customer edge

ConcernWhy REST wins here
Client diversityHTTP and JSON work in every language with zero tooling. gRPC needs codegen, distributed proto files, and HTTP/2 on the caller's side
Debuggabilitycurl, Postman, request logs. These integrations get debugged at 2am by a customer's developer you will never meet. gRPC is binary
Network realityCorporate proxies, WAFs, and older load balancers speak HTTP/1.1 natively. gRPC through enterprise networks is a real support burden
Convention fitIdempotency-Key, HMAC-signed webhooks, and cursor pagination are all HTTP-native conventions the industry already converged on
FamiliarityStripe, Adyen, Plaid, Square are all REST. Novelty is a cost your customers pay

gRPC behind your own API layer

The call from your API service to the ledger, the risk scorer, or the bank-partner adapter. You control both ends, volume is high, latency matters, and strong typing earns its keep.

The two-tier answer is the good one. REST at the edge because I do not control the client, gRPC internally because I do.

GraphQL, no

These are a small fixed set of resources with mutations that must be idempotent, auditable, and individually rate-limited. GraphQL's value is flexible client-driven queries over a rich graph, which you do not have. You would pay for a query planner, harder rate limiting, murkier idempotency semantics, and a worse audit trail, and get nothing back.

Action endpoints beat a generic PATCH

POST /payment_sessions/{id}/cancel is not strictly RESTful. A purist wants PATCH with { state: "canceled" }. The action endpoint is correct and the purist version is wrong here.

A PATCH on state implies the client may set arbitrary states. You would immediately need a whitelist of permitted transitions, which is the action endpoints again with extra steps and a bigger blast radius if the whitelist is wrong.

Same principle as everywhere else in both designs. The client names an intent, the server decides what it means. Stripe has /cancel, /capture, /confirm for exactly this reason.

What customers actually use

Ship official SDKs wrapping the REST API. Typed methods, retries with backoff, idempotency key generation, webhook signature verification. The SDK gives ergonomics, REST underneath gives universality, and anyone in a language you do not support can still curl it. Worth noting that webhooks are also plain HTTP POST, so the customer needs exactly one protocol in both directions.

8. The first three minutes — which problem am I in

The two designs are near-identical until the OAuth leg completes, then they diverge hard. Ask these before you commit, because getting it wrong costs you the back half of the interview.

AskWhat the answer decides
"Does money actually move, or am I returning a credential the customer uses later?" Root 1 and Root 2 both hinge on this. It is the single highest-information question in either interview.
"Is there an amount, and who asserts it?" Whether the customer's server secret is load-bearing for correctness or just for auth. Whether you need money-layer idempotency.
"What is the customer's terminal event, a token or a notification?" Two-token or three-token gradient. Whether webhooks are optional or the whole integration.
"One-shot, or does the user come back?" Access token TTL, and whether a mandate or item store exists at all. Scope this out loud early or it ambushes you at minute 50.
If pay-by-bank: "Which rail, and do we underwrite the return risk?" Whether succeeded is terminal, whether you need a risk-hold state, and whether the rail is pull-based (ACH) or push-only (RTP, FedNow), which changes the state machine entirely.

9. Where to spend your depth

If it is Link

  • Redirect rehydration. The SPA has amnesia. Two independent recovery paths. This is the core problem of that design.
  • The three-token gradient and why the middle token can safely sit in a browser.
  • The nonce. Server-generated, single-use, atomic burn, and why a client-side compare proves nothing.
  • Guarded POST versus safe GET and why refresh, back, and double-click are all safe.

If it is pay-by-bank

  • Settlement. The gap between the user leaving and the rail answering. This is what the question is actually testing.
  • Exactly-once at the debit. The guarded insert, the transactional outbox, and the honest admission that the commit-to-rail gap needs a sweeper.
  • Webhook delivery. At-least-once, deliberately unordered, signed, with a pull-based recovery path.
  • The popup, and why it is a conversion decision rather than a security one.

10. Recap script for either

The shared opening, valid for both. "The customer's backend creates a session with a server secret, which is what keeps the browser from asserting anything that matters. That returns a short-lived scoped token, safe to hand to the browser because of what it cannot do. Their page loads our SDK, which injects an iframe from our origin, and that iframe is the isolation boundary in both directions. The bank cannot be framed, so the OAuth leg has to occupy a top-level context. We send a server-generated single-use nonce out with the redirect, and on the way back we burn it with one atomic conditional update before exchanging the code, so a double-click or a prefetch cannot exchange twice. The server owns the flow state throughout and the client only renders it."

Then Link continues. "On success the widget emits a public_token, which is inert on its own. The customer's backend exchanges it server-to-server for the access_token, which never touches a browser. The whole middle token exists because a credential has to cross an untrusted channel to reach a third party."

Or pay-by-bank continues. "Coming back from the bank means consent, not payment. We check balance, score risk, then insert a payment row whose unique constraint on session id is the real double-charge defense, writing the outbox event in the same transaction. The rail answers in days, so the merchant learns the outcome from a signed, at-least-once, deliberately unordered webhook, backed by a cursor endpoint because a push-only integration is never complete. Nothing is ever handed to the merchant, which is why there is no third token here."

Four lines that carry both designs. The server owns the flow state, the client only renders it. · The client is a courier, not a judge. · Every credential the browser holds is safe to leak. · Push the invariant down to the layer that can enforce it.
