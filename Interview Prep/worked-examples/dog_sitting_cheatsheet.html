Dog-Sitting App — Worked Example

Rover/Wag-style · 1.5M owners, 1M sitters · geo + time search · no double-booking · extension: recurring walks with pickup/dropoff + lockbox codes. A teaching walkthrough.

1. Requirements

Functional

  • Owner: search sitters available in a time range near them; CRUD their upcoming bookings.
  • Sitter: add/remove availability and rates; view upcoming bookings.
  • Extension: recurring walks (weekly MWF or daily). Owner chooses to drop the dog at the sitter's place or have the sitter pick up. Pickup gives the sitter a lockbox code.

Non-functional (the drivers)

  • Search is a geospatial + time-window query — the read hot path.
  • Booking needs consistency: a sitter is never double-booked for overlapping times.
  • Scale: 1.5M owners, 1M sitters. Read-heavy on search, low write volume, low contention.
  • Lockbox codes are sensitive — treat as secrets, not data fields.

Core tension, and the right-sizing note that scores: this is a consistency-on-booking problem like Ticketmaster, but without the hot-key contention. No single sitter is fought over by millions, so the correctness fix is far cheaper.

2. Architecture

Two paths. Read: geo+time search served from a derived index (CDC-fed). Write: booking goes through the Booking service into a bookings DB sharded by sitterId, where an overlap exclusion constraint makes double-booking structurally impossible. Redis and the secrets service are optional/extension pieces.

3. Core entities

Schema

Sitter {
  id, name, location: (lat,lng),
  geoCell,            // S2/geohash id
  rates, serviceTypes,
  willTravel, travelRadius
}
Availability {
  sitterId, during: tstzrange   // open window
}
Booking {
  id, ownerId, sitterId,
  during: tstzrange,            // the slot
  status: pending|confirmed|cancelled,
  serviceType, locationOption   // sit|walk
}                               // dropoff|pickup

Decisions to defend

  • Time slots are ranges (tstzrange), not start/end columns, so the DB can enforce non-overlap natively (§5).
  • geoCell is precomputed from lat/lng so search is an index lookup, not a per-row distance scan (§4).
  • Money as integer minor units; format at render.
  • Location is static, availability is not — so the search index is a derived read model kept fresh by CDC, eventually consistent by seconds, re-checked at booking time.

4. Geospatial search (the read hot path)

The query is "sitters within X miles of me, available between T1 and T2." You cannot scan a million sitters and compute distance to each per search, so you need a spatial index. The shared idea behind all of them is to convert a 2D location into a locality-preserving 1D key, so physically-near sitters share a key prefix and become range-scannable.

Index options (name the trade-off)

OptionTrade
GeohashSimplest, fits any B-tree/Redis. Boundary effects — query target cell + 8 neighbors.
QuadtreeAdapts to density (fine cells in cities). More upkeep.
S2 / H3Production-grade cells, handle boundaries/distortion well.
PostGISGiST index + ST_DWithin radius queries. The pragmatic pick at 1M rows if you're on Postgres.

Two-stage query

  • Coarse spatial cut: map the radius to covering cells, pull candidate sitters in those cells — a million rows down to hundreds.
  • Fine filter on the small set: available in [T1,T2], not already booked; then rank by distance, rating, price.
  • Cheap spatial cut first, expensive filters on the candidates — same retrieval-then-ranking shape as text search.

The index (cells + current availability) is a derived read model fed by CDC. Availability edits flow through, the index goes stale by seconds, which is fine because the booking step re-checks truth.

5. No double-booking (the Ticketmaster lesson, right-sized)

Enforce it in the database

CREATE EXTENSION btree_gist;
ALTER TABLE bookings
  ADD CONSTRAINT no_overlap
  EXCLUDE USING gist (
    sitter_id WITH =,
    during    WITH &&      -- tstzrange overlap
  ) WHERE (status = 'confirmed');

Two rows with the same sitter_id and overlapping ranges cannot both exist. The DB rejects the second insert atomically, so a double-booking is structurally impossible — not a check-then-insert that can race.

Why this, and why it's simpler than Ticketmaster

  • Same principle as Ticketmaster's SET NX / FOR UPDATE: make correctness a property the datastore enforces, not something the app hopes it checked in time.
  • Shard by sitterId so all of one sitter's bookings colocate → the overlap check + insert is a single-shard transaction, no 2PC. (Shard by the entity you transact against.)
  • No waiting queue, no Redis lock needed by default — contention is low, one sitter isn't a hot key like one concert. Reaching for a queue here is over-engineering.

When you'd add a hold

If there's a checkout/payment step, hold the slot with a pending row (already blocked by the constraint) or a Redis key with a TTL, à la reserved_until. Say you considered it and the workload doesn't require it — that's the senior move.

6. Extension: recurring walks, pickup/dropoff, lockbox codes

Three changes. The core booking-consistency machinery doesn't move — each walk is just another booking flowing through the same exclusion constraint, which is the sign the model was factored well.

Recurring walks — materialize, don't just store a rule

WalkSeries {
  id, ownerId, sitterId,
  rrule,              // "weekly MWF" | "daily"
  window, locationOption, lockboxRef
}
// expand into concrete bookings:
Booking { …, seriesId }   // one per occurrence
  • Store the recurrence rule, but materialize individual booking instances for a rolling horizon (next 4–8 weeks). You can't enforce non-overlap on a rule you haven't expanded — each occurrence must reserve a real slot.
  • A background job extends the horizon as time passes.
  • Edit/cancel is "this instance vs whole series" — the Google-Calendar problem. An instance can override or detach from its series.

Pickup vs dropoff, and the lockbox secret

  • locationOption: dropoff = service at sitter's place (search already assumed this). Pickup = sitter travels to owner, so owner location now matters — filter sitters by willTravel/radius and account for travel time between back-to-back walks.
  • Lockbox code = a secret, not a field. Store encrypted/tokenized, never plaintext, never in logs or analytics.
  • Scope + time-bound: valid only for this sitter, this walk, and only in a window around the scheduled time. Reveal to the sitter's app just before the walk, not at booking.
  • Rotate per series or per instance so last Monday's code doesn't open the box next Monday, and audit every access.

Same "short-lived, scoped, rotated, audited, never logged" token discipline from fintech, applied to a physical key.

Summary of design changes: add a WalkSeries entity + a materialization job; extend Booking with serviceType, locationOption, seriesId, and a lockbox-credential reference; add a small secrets service with its own lifecycle for codes; extend geo-eligibility to consider the owner's location for pickups. The overlap constraint and sitter-sharding are untouched.

7. Follow-ups — answers to have ready

Why don't you need Redis locks or a waiting queue like Ticketmaster?

Contention. Ticketmaster had 10M people racing for one event, a genuine hot key, so it needed a queue to shed load and Redis locks to serialize. Here, a single sitter is booked by at most a handful of owners, and rarely simultaneously, so a row-level DB exclusion constraint fully serializes the rare conflict with no extra infrastructure. Using the heavy tool only when load demands it is the point — I'd name that I considered it and rejected it.

Two owners try to book the same sitter for overlapping times at once — walk the race.

Both transactions attempt to insert a confirmed booking for that sitter_id with overlapping during. The exclusion constraint lets the first commit; the second violates the constraint and is rejected atomically by the DB. The loser gets a clean "no longer available" and re-queries. No application-level check-then-insert window exists, so there's nothing to race.

How do you keep the search index's availability fresh?

CDC from the sitter/availability DB into the geo/search index, same as the tweet-search pattern. It's eventually consistent by seconds, which is fine for browsing — the booking step re-checks the authoritative DB and its constraint, so a stale "available" just yields an occasional "just taken" at booking, never a double-booking.

Pickup walks change the geo query — how?

For dropoff, the sitter's location is what matters and the existing cell index works. For pickup, eligibility depends on sitter-to-owner distance and the sitter's willTravel radius, so you filter candidates by whether the owner falls inside each sitter's travel range, and you must leave travel time between consecutive pickups (a scheduling constraint on top of the overlap one).

Does the recurring series need distributed transactions across occurrences?

No. Each occurrence is a separate booking row for one sitter, and all of a sitter's bookings live on the same shard (sharded by sitterId), so materializing a MWF series is a set of single-shard inserts, each independently checked by the constraint. If one occurrence conflicts, only that instance fails; you surface it and let the owner adjust that date.

Where does the lockbox code live, and who can read it?

In a secrets service, encrypted, referenced by the booking but not stored on it. Only the assigned sitter's app can fetch it, only during the walk window, and every fetch is audited. It rotates per series/instance. It never appears in logs, analytics, or the search index. Treat it exactly like a scoped, short-lived credential.

8. Numbers to drop

Scale

1M sitters is small — profiles + availability fit comfortably in one sharded Postgres with read replicas. The dataset doesn't force exotic infrastructure; the interesting parts are the geo index and the overlap constraint, not raw scale.

Search

Spatial cut takes ~1M candidates to hundreds per query; the fine filter + ranking runs on that small set. Cache popular (location, time-window) query results in Redis; a sitter's availability changes rarely enough that short TTLs are safe.

9. 30-second recap script

Two paths with different priorities. Search is a geospatial-plus-time read: precompute each sitter's S2 or geohash cell, do a coarse spatial cut to a few hundred candidates, then filter by availability and rank by distance and rating, serving it from a CDC-fed derived index that's stale by seconds. Booking is the consistency path: model slots as time ranges and add a Postgres exclusion constraint so two overlapping confirmed bookings for the same sitter can't coexist, making double-booking structurally impossible rather than app-checked. Shard the bookings table by sitter id so that check plus the insert is a single-shard transaction with no 2PC. Crucially, unlike Ticketmaster there's no hot-key contention, so no waiting queue and no Redis lock are needed — a row-level constraint suffices, and I'd say I considered the heavier tools and rejected them. For the recurring-walks extension, store a recurrence rule but materialize concrete booking instances so each occurrence passes the same overlap check, add a pickup-or-dropoff option that pulls owner location into the geo eligibility for pickups, and treat the lockbox code as a scoped, short-lived, rotated, audited secret revealed to the sitter only around the walk time.
