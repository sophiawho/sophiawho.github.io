Plaid Link — Frontend Systems Design

Embeddable account-linking widget · RADIO · deep dives: security, OAuth redirect, idempotency

PART ONE — the answer you produce · requirements, architecture, credentials, interfaces, recap

1. Requirements in one line

Functional

  • Embeddable widget returns a public_token on successful link
  • OAuth redirect auth — user authenticates on the bank's page, we never see credentials
  • In-widget institution search + selection
  • Flow: CONSENT → SELECT_INSTITUTION → OAUTH_REDIRECT → OAUTH_RETURN → ACCOUNT_SELECT → SUCCESS

Non-functional

  • Security & isolation — iframe, postMessage allowlist, CSRF state, no secret in browser PRIMARY DEEP DIVE
  • Idempotency & resilience — survive refresh, back, double-click, new-tab redirect; no duplicate links
  • a11y (focus trap, ESC, ARIA), cross-device (mobile = full redirect), i18n
  • Out of scope: SEO, initial-load perf
Frame it as "an SPA that must rehydrate cleanly after a redirect," not CSR vs MPA. The server owns the flow state; the client only renders it.

2. Architecture & trust boundary

The pieces

  • Host page loads a small JS SDK (create/open) that injects an iframe → Widget SPA, served from our origin.
  • postMessage bridge iframe ↔ host for lifecycle events (READY, SUCCESS, EXIT). Origin-checked both ways.
  • Widget → our backend over HTTPS; our backend ↔ bank OAuth. Customer backend exchanges public_token server-to-server.

Trust boundary say it out loud

  • Credentials live only between the user's browser and the bank. That one line answers half the security questions.
  • The iframe (same-origin policy) is what stops the customer's page from reading inside the widget.
  • Token gradient: link_token in → public_token out → access_token never touches the browser.

3. Data model and credentials

LinkSession — server owns it

One row the server owns; must survive the OAuth redirect. Client holds only the link_token breadcrumb that resolves to it.

  • session_id — internal PK (~4h lifetime), never rides a bank redirect URL
  • link_token — client-facing bearer credential, short-lived
  • current_step — authoritative FlowState, client renders, never asserts
  • institution_id, selected_accounts — client proposes, server persists
  • oauth_state_id — server-generated single-use nonce for the current OAuth leg; burned on use

Credentials — two kinds, keep them apart

Secrets are long-lived, server-only, and identify a party. Tokens are short-lived, scoped, and identify a thing in flight.

There are two separate chains and merging them is the classic mistake. Chain A is the bank OAuth chain, authorization code exchanged with our client secret for a bank token that never leaves our servers. Chain B is the customer-facing chain, link_token then public_token then access_token. Nothing in chain B ever "becomes" the bank token. The Plaid access_token is our own handle to the Item, so even the customer never touches a bank credential.

Every step that mints a stronger credential happens on a server holding a secret. Chain B is three tokens long only because a credential has to reach a third party through an untrusted channel.

5. 30-second recap script

Host page loads our SDK, which injects an iframe widget from our origin — the iframe is the isolation boundary, credentials only ever pass between the browser and the bank. Server mints a LinkSession and owns the authoritative FlowState; the client holds only a short-lived link_token and renders whatever step the server reports. At OAuth we redirect out to the bank with a single-use oauth_state_id; on return the SPA has amnesia, so it recovers the session (sessionStorage or the state in the URL), fires one guarded POST to finalize exactly once, then a safe GET to render. Idempotency-Keys and the single-use nonce guarantee at most one link. The public_token goes up to the customer's backend, which exchanges it server-to-server for the access_token — which never touches the browser.
PART TWO — deep dives · pull these out when probed

6. OAuth redirect and rehydration CORE PROBLEM

The SPA reloads from scratch (amnesia). Question on return: which session is this browser? Two independent recovery paths: (1) sessionStorage breadcrumb = link_token, works same-tab; (2) oauth_state_id in the callback URL, server looks up the session, works new-tab with empty storage. The client is a courier, not a judge — a client "state I sent vs got back" check proves nothing; the server generated + stored the state and does the only comparison that counts. Client just forwards state+code, then GET /link/session/:id and renders whatever step the server reports.

Why a guarded POST and a safe GET

Different questions. GET = "where am I, what do I render" — read-only, refresh five times, nothing breaks. POST /oauth/callback = "finalize this grant exactly once" — validates state (CSRF), checks single-use (replay), exchanges the code, burns the state, advances the step. It is a write, so it wants to be a POST.

Do not overstate this, because an interviewer may catch it. The bank's redirect back is always a GET — that is the OAuth spec plus browser behaviour on a 302, and you do not get to choose the method. So a perfectly standard design points redirect_uri straight at a backend endpoint that handles the GET, burns the nonce inline, exchanges the code, then 303s to a clean URL with no query string. Reload then re-requests the clean page, not the callback. The nonce is precisely what makes that unavoidable GET safe.

7. Why the public_token rides the browser

Natural interviewer question. Why not just have our backend push it to the customer's backend? Four reasons, and the best one is not the obvious one.

What the browser hop buys

  • User identity for free. When their frontend POSTs the token to their own backend, that request rides their own session cookie. They know exactly which of their users just linked, from their own auth system. A server push would force them to correlate on some client_user_id we echoed back, which means trusting a field we sent rather than their own login state.
  • No webhook endpoint required. Many integrations are small teams. Demanding a publicly reachable, signature-verifying endpoint just to complete the basic flow is a brutal onboarding barrier.
  • The exchange becomes their deliberate act. They call exchange with their secret, and that is when they take ownership of the Item and start being billed. Pull beats push when the receiving side incurs an obligation.
  • Latency. The user is sitting there. You need a browser signal regardless, so the only question is whether the token rides along or arrives separately, and separate is strictly more plumbing.

Why it is safe, and what it costs

Safe only because of what the token is. Short-lived, single-use, and completely inert without the customer's secret. If it were not inert this design would be wrong and you would be forced to the server path.

The cost, and name it before they ask. The handoff can drop. User succeeds, the widget emits the token, they close the tab before the POST lands. The Item now exists on our side and the customer never learned about it. That is an orphaned link and a support ticket.

Which is why the browser path is not the only path. Webhooks cover what the browser cannot — OAuth completing in a context the original page did not survive, item errors, re-auth prompts. The browser hop is the happy path and the webhook is the safety net, not an either-or.

The rule that generalises, and it is worth saying. The delivery mechanism follows from whether the answer exists while the user is still present. In Link it does, so you hand it through the browser and gain identity, latency, and a simpler integration. In a payments widget the outcome arrives days after the tab closed, so a browser handoff is impossible and webhooks are forced, along with the outbox and the cursor endpoint. Same choice, different constraint.

8. Exactly-once, and the nonce

UI shows a step only after the server confirms it — model illegal transitions as rejected so a stale message or duplicated redirect can't jump forward. First callback wins and burns the state, the second is rejected. OAuth retry mints a fresh oauth_state_id, invalidating the old one for free. Invariant: at most one link created.

Burn it atomically, and burn it first

UPDATE oauth_state SET used_at = now()
 WHERE state = $1 AND used_at IS NULL AND expires_at > now();
-- assert rows_affected == 1, else reject

token = exchangeWithBank(code);   -- only AFTER the claim

A SELECT then UPDATE is a race. Two concurrent callbacks from a double-click or a prefetch both read used_at IS NULL and both exchange, and the window is as wide as a network call to a bank. Claim first, then do the slow thing. If the exchange fails afterwards the nonce stays burned and the user retries with a fresh one, which is correct.

9. Security — three separate boundaries

(1) iframe isolation — same-origin policy blocks the customer page from reading widget JS/DOM. (2) postMessage channel — pin the exact target origin on send, check event.origin against the allowlist on receive (exact string match, never includes — evil-customer.com.attacker.com passes a naive substring check). (3) CSRF state — server-generated, session-bound, single-use oauth_state_id on the redirect; forged callbacks fail the match, replays fail single-use.

The trust rule, stated precisely

The client only ever holds values that are safe to leak: link_token (expires fast), oauth_state_id (useless once burned), public_token (inert without the secret). Server-only: customer secret creds, access_token, and the authority to validate/burn a nonce. A client-generated nonce is worthless for CSRF.

10. Edge cases and abuse

Every FlowState has an ERROR edge (bank down, state mismatch, expired). Cancel/ESC → EXIT, session marked abandoned. expires_at (~4h) rejects late transitions. Rate-limit session creates / OAuth attempts per link_token / IP / customer; monitor nonce-failure spikes (forged-callback probing). Back button is safe: GET re-fires freely, the finalize POST is protected by the burned nonce + Idempotency-Key.
