Plaid Link — Frontend Systems Design

Embeddable account-linking widget · RADIO · deep dives: security, OAuth redirect, idempotency

1. Requirements in one line

Functional

  • Embeddable widget returns a public_token on successful link
  • OAuth redirect auth — user authenticates on the bank's page, we never see credentials
  • In-widget institution search + selection
  • Flow: CONSENT → SELECT_INSTITUTION → OAUTH_REDIRECT → OAUTH_RETURN → ACCOUNT_SELECT → SUCCESS

Non-functional

  • Security & isolation — iframe, postMessage allowlist, CSRF state, no secret in browser PRIMARY DEEP DIVE
  • Idempotency & resilience — survive refresh, back, double-click, new-tab redirect; no duplicate links
  • a11y (focus trap, ESC, ARIA), cross-device (mobile = full redirect), i18n
  • Out of scope: SEO, initial-load perf
Frame it as "an SPA that must rehydrate cleanly after a redirect," not CSR vs MPA. The server owns the flow state; the client only renders it.

2. Architecture & trust boundary

The pieces

  • Host page loads a small JS SDK (create/open) that injects an iframe → Widget SPA, served from our origin.
  • postMessage bridge iframe ↔ host for lifecycle events (READY, SUCCESS, EXIT). Origin-checked both ways.
  • Widget → our backend over HTTPS; our backend ↔ bank OAuth. Customer backend exchanges public_token server-to-server.

Trust boundary say it out loud

  • Credentials live only between the user's browser and the bank. That one line answers half the security questions.
  • The iframe (same-origin policy) is what stops the customer's page from reading inside the widget.
  • Token gradient: link_token in → public_token out → access_token never touches the browser.

3. Data model & the token gradient

LinkSession — server owns it

One row the server owns; must survive the OAuth redirect. Client holds only the link_token breadcrumb that resolves to it.

  • session_id — internal PK (~4h lifetime), never rides a bank redirect URL
  • link_token — client-facing bearer credential, short-lived
  • current_step — authoritative FlowState, client renders, never asserts
  • institution_id, selected_accounts — client proposes, server persists
  • oauth_state_id — server-generated single-use nonce for the current OAuth leg; burned on use

Token gradient weaker toward the browser

TokenRole / lifetimeLives
link_tokenEntry ticket · min–hrBrowser (scoped, expiring)
public_tokenClaim check, inert · ~30mBrowser → cust. backend
access_tokenPulls data · long-livedServer only. Never browser.

Every step that mints a stronger token happens on a server holding a secret.

5. Deep dives — answers to have ready

OAuth redirect & rehydration CORE PROBLEM

The SPA reloads from scratch (amnesia). Question on return: which session is this browser? Two independent recovery paths: (1) sessionStorage breadcrumb = link_token, works same-tab; (2) oauth_state_id in the callback URL, server looks up the session, works new-tab with empty storage. The client is a courier, not a judge — a client "state I sent vs got back" check proves nothing; the server generated + stored the state and does the only comparison that counts. Client just forwards state+code, then GET /link/session/:id and renders whatever step the server reports.

Why a guarded POST and a safe GET

Different questions. GET = "where am I, what do I render" — read-only, refresh five times, nothing breaks. POST /oauth/callback = "finalize this grant exactly once" — validates state (CSRF), checks single-use (replay), exchanges the code, burns the state, advances the step. Burning a nonce is a side effect, so it can't live on a GET (a refresh/prefetch would blow up the session).

Idempotency & no optimistic advance

UI shows a step only after the server confirms it — model illegal transitions as rejected so a stale message or duplicated redirect can't jump forward. First callback wins and burns the state; the second is rejected or deduped. OAuth retry mints a fresh oauth_state_id, invalidating the old one for free. Invariant: at most one link created.

Security — three separate boundaries

(1) iframe isolation — same-origin policy blocks the customer page from reading widget JS/DOM. (2) postMessage channel — pin the exact target origin on send, check event.origin against the allowlist on receive (exact string match, never includes — evil-customer.com.attacker.com passes a naive substring check). (3) CSRF state — server-generated, session-bound, single-use oauth_state_id on the redirect; forged callbacks fail the match, replays fail single-use.

The trust rule, stated precisely

The client only ever holds values that are safe to leak: link_token (expires fast), oauth_state_id (useless once burned), public_token (inert without the secret). Server-only: customer secret creds, access_token, and the authority to validate/burn a nonce. A client-generated nonce is worthless for CSRF.

Edge cases & abuse

Every FlowState has an ERROR edge (bank down, state mismatch, expired). Cancel/ESC → EXIT, session marked abandoned. expires_at (~4h) rejects late transitions. Rate-limit session creates / OAuth attempts per link_token / IP / customer; monitor nonce-failure spikes (forged-callback probing). Back button is safe: GET re-fires freely, the finalize POST is protected by the burned nonce + Idempotency-Key.

6. 30-second recap script

Host page loads our SDK, which injects an iframe widget from our origin — the iframe is the isolation boundary, credentials only ever pass between the browser and the bank. Server mints a LinkSession and owns the authoritative FlowState; the client holds only a short-lived link_token and renders whatever step the server reports. At OAuth we redirect out to the bank with a single-use oauth_state_id; on return the SPA has amnesia, so it recovers the session (sessionStorage or the state in the URL), fires one guarded POST to finalize exactly once, then a safe GET to render. Idempotency-Keys and the single-use nonce guarantee at most one link. The public_token goes up to the customer's backend, which exchanges it server-to-server for the access_token — which never touches the browser.
