Ticketmaster — System Design Cheatsheet

Search (availability) · Booking (consistency, no double-sell) · 10M users on 1 event · read-heavy 100:1 · <500ms search

1. Requirements in one line

Functional

  • View events; search by name, date, city (or combo)
  • View one event + its available tickets/seats
  • Book one or more tickets to an event

Out of scope

  • Viewing booked events, adding events, dynamic pricing, GDPR, backups, CI/CD

Non-functional (the real design drivers)

  • Search: prioritize availability — stale-by-seconds is fine
  • Booking: prioritize consistency — never double-sell a seat
  • Scalable: 10M users hitting one popular event at once
  • Low-latency search <500ms; read-heavy 100:1

The split personality (availability for search, consistency for booking) is the whole interview. Say it up front.

2. Core entities & schema

Tables (Postgres, ACID)

Event    { id, venueId, performerId,
           name, description, date }
Venue    { id, location, seatMap }
Performer{ id, name }
Ticket   { id, eventId, seat, price,
           status: available|reserved|booked,
           userId }
Booking  { id, userId, ticketIds[],
           status: pending|completed|failed }

Why relational / ACID here

  • Booking needs transactions — flip N tickets + create booking atomically.
  • Ticket status is the source of truth for "sold". Must be strongly consistent.
  • Rich search filters (name/date/city) map to a normalized schema; the heavy search load is offloaded to Elasticsearch, not run on the primary.

Ticket state lives in the DB. Redis holds a short-lived lock, never the truth.

3. API interfaces

Reads (availability path)

GET /events?search_term=&location=&date=
   → [Event]      (search by any combo)

GET /events/{id}
   → Event + available tickets

Writes (consistency path)

POST /bookings
   Idempotency-Key: <uuid>
   { eventId, ticketIds: string[] }
   → { bookingId }        (reserves, TTL)

POST /bookings/{id}/payment
   → confirmation         (commits sale)

Two-step: reserve first (lock seats), pay second (finalize). Client generates the idempotency key.

4. Architecture

Two paths. Read path: Client → CDN → Gateway → Search (Elasticsearch) or Event svc (Redis → replicas). Write path: Gateway → (waiting queue if hot) → Booking svc → Redis lock → leader Postgres → Stripe.

5. Search path (availability, <500ms)

How

  • Reads served from Elasticsearch — inverted index over name/date/location, fast fuzzy/partial matches.
  • ES stays fresh via CDC (change-data-capture) streaming from Postgres. Eventually consistent by seconds — fine for search.
  • Cache popular query results + hot event pages in Redis; static assets on CDN.

Why this scales the 100:1 read ratio

  • Search never touches the write leader → booking throughput is protected.
  • Read replicas of Postgres absorb GET /events/{id} misses. Leader only takes writes.
  • Available seat count is intentionally cached/stale — the truth is re-checked atomically at booking time, so a stale "12 left" is harmless.

6. Elasticsearch & CDC (deep dive)

DB is truth, ES is a derived read model

  • Writes go to Postgres. A CDC stream (Debezium tailing the WAL, or an outbox table) propagates event changes to ES asynchronously.
  • ES is eventually consistent, stale by seconds — acceptable because booking re-checks truth on the leader. Never book off the search index.
  • Make the sync idempotent: upsert by eventId, so replays/duplicates are safe. Reconcile ES against Postgres periodically to heal CDC gaps.
Postgres --WAL--> CDC (Debezium)
         --> Kafka --> ES upsert(eventId)

ES doesn't replace the Redis cache

ES has internal caches, but none is an app-layer read-through store:

  • Shard request cache — full query result per shard, keyed by request. Helps exact repeats/aggregations; cleared on refresh.
  • Query/filter cache — bitsets of which docs match a filter (e.g. city=SF) per segment.
  • OS page cache — the real reason ES is fast: memory-mapped Lucene segments live in RAM.

Keep Redis in front for hot event pages / exact-repeat queries: sub-ms, you control the TTL. Different job than ES.

7. Booking path — no double-sell (deep dive)

Reserve → Pay, with a Redis lock

POST /bookings {eventId, ticketIds}
1. For each ticketId, SET NX in Redis:
     SET lock:{ticketId} {userId}
         NX EX 600          (10-min TTL)
   Multiple tickets → acquire in sorted
   order (avoid deadlock), atomic.
2. Any SET NX fails → seat taken →
   release the ones you got → 409.
3. All locks held → Booking row
   (status=pending), return bookingId.

POST /bookings/{id}/payment
4. Stripe charge succeeds →
   TXN: tickets.status=booked,
        booking.status=completed,
        delete Redis locks.

Why a Redis lock + TTL

  • SET NX is atomic — first writer wins, so two users can't both reserve the same seat.
  • TTL auto-releases seats if a user reserves then abandons checkout. No cron/cleanup job needed.
  • Lock is a fast-path reservation; the DB transaction at payment is the durable source of truth. Lock disagreeing with DB is safe because DB wins.

Belt-and-suspenders (defend it)

The final commit re-checks ticket.status='available' inside the transaction (or uses SELECT ... FOR UPDATE / optimistic version column). If Redis ever fails open, the DB still refuses a double-sell. Redis is an optimization for the common case, not the correctness guarantee.

Pick ONE reservation store — this vs §11 are alternatives, not a stack

The Redis SET NX + TTL here and the DB SKIP LOCKED in §11 both hold a reservation. Don't run both — two stores drift (Redis key expires but the DB row stays reserved forever). The choice follows the seat-selection model:

  • User picks a specific seat (this section) → Redis SET NX per ticketId, TTL auto-releases. DB row stays available until payment; Redis is the only reservation store.
  • Server assigns seats under heavy contention (§11, popular onsale) → skip Redis entirely. Reservation lives in the DB as status='reserved' + reserved_until, reclaimed lazily + by a sweeper. SKIP LOCKED removes the stale-read window that Redis was there to paper over.

8. Idempotency (deep dive)

Problem

Client retries POST /bookings (timeout, double-tap, flaky network). Without protection you reserve/charge twice.

Mechanism

  • Client sends a UUID Idempotency-Key per logical booking attempt.
  • Server stores idem:{key} → {status, bookingId} in Redis on first receipt (SET NX).
  • Retry with same key → return the stored result, don't re-execute.

Where it matters most

  • Payment is the dangerous one. Pass the idempotency key through to Stripe — Stripe dedupes charges by key, so a retry never double-charges.
  • Make ticketIds the natural idempotency scope: re-reserving seats you already hold is a no-op, not a conflict.
  • Store idempotency records with a TTL (e.g. 24h) — long enough to cover retries, short enough to reclaim memory.

One line to say: "Every mutating call is safe to retry — client key on POST /bookings, same key forwarded to Stripe for the charge."

9. Replicas & leader-follower (deep dive)

Topology

  • Single leader takes all writes (bookings/ticket state) → keeps consistency simple, one authority per seat.
  • Read replicas stream from the leader and serve GET /events/{id}, availability counts, CDC to Elasticsearch.
  • Shard by eventId so one megaevent's booking load lands on its own partition and doesn't starve others.

Trade-offs to name

  • Replica lag → availability counts can read slightly stale. Acceptable: booking re-checks truth on the leader atomically.
  • Never read seat availability from a replica for the final commit — that must hit the leader (or the row lock) to avoid double-sell.
  • Leader failover: promote a replica; brief write pause. Booking is paused, not incorrect — the right failure mode for a consistency-first path.
  • Sharding by eventId keeps every ticket for one event co-located → single-partition transactions, no cross-shard 2PC.

10. Popular events — the virtual waiting queue (deep dive)

Why

10M users refreshing one event will crush the booking service and Redis locks. You can't lock-check 10M/s. Shed load before it reaches the booking path.

How (Redis)

On event open, gate entry:
  queue:{eventId}   → sorted set of
                       sessionIds by ts
  admitted:{eventId}→ set of allowed

Admit a steady trickle (e.g. N/sec)
from the front of the queue into the
real booking flow. Everyone else waits
and sees position + ETA.

What it buys you

  • Booking service sees a bounded request rate (admission rate), not the full 10M spike → predictable, no meltdown.
  • Fairness: FIFO by arrival timestamp, not "fastest refresher wins".
  • Backpressure lives in cheap Redis, not in Postgres or Stripe.
  • Admitted users get a token (short TTL) allowing them into POST /bookings; token expiry returns their slot.

Only turn the queue on for flagged high-demand events — normal events skip it entirely.

11. Seat assignment by section + quantity (deep dive)

Server picks the seats, not the user

The go-to for popular onsales. User picks a section and a quantity, not specific seats. Server atomically selects and reserves the best available block in one statement — no human between the read and the write, and no Redis. Reservation state lives in the DB.

BEGIN;
SELECT id FROM tickets
  WHERE eventId=? AND section=?
    AND (status='available'
      OR (status='reserved'
          AND reserved_until < now()))
  ORDER BY seat_quality
  LIMIT ?                     -- qty
  FOR UPDATE SKIP LOCKED;     -- key
UPDATE tickets
  SET status='reserved', userId=?,
      reserved_until = now()+'10 min'
  WHERE id IN (...);
COMMIT;

Why it works

  • No stale-read window. Selection and reservation are the same atomic step, so there's nothing to go stale in between.
  • SKIP LOCKED makes concurrent requests walk past each other's locked rows instead of colliding — roughly one success per available seat, not thousands fighting over the same few hundred attractive ones.
  • Success rate is bounded by real inventory, not contention. Kills the retry storm since almost nobody loses a race.

Expiry without Redis

The txn is short — pick, flip to reserved, commit. It does not hold the row lock for the 10-min checkout (that would pin a connection). The reserved status is what keeps other pickers off. Abandoned carts are reclaimed lazily (the reserved_until < now() predicate treats them as free) plus a light sweeper for count accuracy. This replaces the Redis TTL from §7.

Cost (defend it)

Users give up specific seat choice. Fine for a general-admission-style onsale; wrong for resale or accessible seating, where the user must pick the exact seat — there you fall back to the per-seat Redis lock in §7.

12. Live seat map — short-interval polling, not SSE (deep dive)

Poll every 1–2s

For high-demand events, clients poll the seat map every 1–2s rather than holding an SSE/WebSocket connection.

  • The response is cacheable: snapshot the map, cache at the edge with a 1s TTL, serve 50k clients with almost no DB load.
  • SSE can't do that — each client needs a live per-connection stream held open on your servers.

Why polling wins here (defend it)

  • Freshness converges anyway. At this scale you'd batch SSE pushes to ~1/s regardless, or you're fanning out millions of msgs/s — so SSE stops being more real-time.
  • Degrades gracefully. A dropped poll = one missed request. 50k dropped SSE connections all reconnect at once and take your servers down.
  • The usual "wasted empty polls" knock doesn't apply — a popular event changes constantly, so nearly every poll returns new data.

Use SSE/WebSocket for low-fanout, truly push-driven cases; for a 50k-viewer onsale map, cached polling is cheaper and more robust.

13. Follow-ups — answers to have ready

User reserves a seat then vanishes

The Redis lock has a 10-min TTL; it auto-releases and the seat returns to available. No sweeper job needed. Availability count is recomputed on read (or the count is decremented/incremented as locks flip).

Two users grab the last seat at the same instant

SET NX is atomic — exactly one succeeds and gets the lock. The loser gets 409 immediately. Even if both somehow reached the DB, the commit's FOR UPDATE / status check lets only one flip the row to booked.

Payment succeeds but the booking write fails

Charge Stripe with the idempotency key after (or coordinated with) flipping ticket state, and treat the booking as an idempotent workflow: on retry, the Stripe key prevents a second charge and the DB txn is re-attempted. If it can't complete, refund via the same key. Prefer capturing payment only once seats are durably committed.

Search shows a seat that's already gone

Expected — search/availability is eventually consistent (CDC + cached counts). The reserve step is the authority: the stale view just means an occasional "sorry, just taken" at booking time, which is acceptable for an availability-first read path.

Multiple tickets in one booking (all-or-nothing)

Acquire locks for all ticketIds in a deterministic (sorted) order to avoid deadlock; if any fails, release the rest and fail the whole booking. Commit all ticket rows in one DB transaction.

Redis (lock store) goes down

Booking is the consistency-first path, so fail closed: the DB transaction with row locking is the real guarantee, so worst case we fall back to DB-only reservation (slower, still correct) or briefly reject bookings. Never fail open into a double-sell.

Why not just lock rows in Postgres and skip Redis?

You can, and the DB is the ultimate guarantee. Redis is there to keep long-held "reserved-but-not-paid" state off the leader and to absorb the popular-event spike cheaply. It's a performance layer in front of the correctness layer.

14. Numbers to drop

Load

Read-heavy 100:1. 10M users on one on-sale → without a queue that's a multi-million/s spike on booking; the waiting queue admits maybe a few thousand/s into the real flow.

Storage / locks

A ticket lock is ~tens of bytes; even a 100k-seat stadium is a few MB in Redis, all TTL'd. Elasticsearch index sized to event catalog, not to traffic.

15. 30-second recap script

Two paths with opposite priorities. Reads favor availability: search hits Elasticsearch (fed by CDC from Postgres), event pages and availability counts are cached in Redis and served from read replicas, so the 100:1 read load never touches the write leader and stays under 500ms. Writes favor consistency: booking is a two-step reserve-then-pay. Reserve does an atomic SET NX Redis lock per seat with a 10-minute TTL so abandoned carts self-release; payment commits a single Postgres transaction that flips ticket status and is the real source of truth — Redis is just a fast reservation in front of it. Every mutation is idempotent via a client UUID key, forwarded to Stripe so retries never double-charge. Postgres is single-leader for writes with read replicas and is sharded by eventId so a megaevent stays on one partition. For a 10M-user on-sale we put a Redis virtual waiting queue in front, admitting a bounded trickle in FIFO order so the booking path never sees the full spike. If Redis dies we fail closed to the DB's row locks — never into a double-sell.
