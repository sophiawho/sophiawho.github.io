React — Forms

Wrap inputs in a <form> so Enter key submits

A <form> with onSubmit handles both button clicks and Enter key — no extra keydown listener needed. The form wraps all related inputs as children; each input still manages its own state independently.

// wrap inputs in a form — Enter OR button click both trigger onSubmit
<form onSubmit={(e) => {
  e.preventDefault();   // required — prevents full page reload
  handleSubmit();
}}>
  <input value={name} onChange={(e) => setName(e.target.value)} placeholder="Name" />
  <input value={email} onChange={(e) => setEmail(e.target.value)} placeholder="Email" />
  <textarea value={notes} onChange={(e) => setNotes(e.target.value)} />
  <button type="submit">Submit</button>
</form>
e.preventDefault() is required. Without it the form triggers a full page reload on submit — the browser's default behavior for forms.
button type matters: type="submit" triggers onSubmit. A button with type="button" inside the form does NOT. The default type for a button inside a form is submit, so you can omit it — but being explicit is clearer.

React — State Update Patterns

Compute everything first, set state at the end

Because state updates don't apply immediately, derive all new values using local variables first. Then commit all the state updates together at the end of the function. This makes the data flow read top to bottom like a recipe.

// ✗ avoid — splitting logic across helper functions forces you to pass
// derived values around and obscures what one event actually does
function updateCell(row, col) {
  const alteredBoard = computeBoard(...);
  setBoard(alteredBoard);
  checkForWinner(alteredBoard);  // must pass in — can't read board, it's stale
  updateTurn();
}

// ✓ idiomatic — compute everything, then set state at the end
function updateCell(row, col) {
  // 1. derive all new values using local variables
  const newState = isXTurn ? 1 : 2;
  const alteredBoard = board.map((r, rIdx) =>
    r.map((cell, cIdx) => rIdx === row && cIdx === col ? newState : cell)
  );
  const hasWinner = gameHasWinner(alteredBoard, newState);
  const playerName = isXTurn ? "Player X" : "Player O";

  // 2. commit all state updates together at the end
  setBoard(alteredBoard);
  setIsXTurn(!isXTurn);
  if (hasWinner) {
    setWinner(playerName);
    setMessage(`${playerName} wins!`);
  }
}
Why you must pass derived values around: setBoard(alteredBoard) doesn't update board immediately — it schedules the update for the next render. So board is still the old value for the rest of the function. Always read from local variables, not state, after a set call.
React state pattern high priority

React batches multiple state updates into one re-render

Multiple set calls in the same event handler don't each trigger a re-render. React waits until the function finishes, then re-renders once with all updates applied.

function updateCell() {
  setBoard(alteredBoard);   // doesn't re-render yet
  setIsXTurn(!isXTurn);    // doesn't re-render yet
  setMessage("X wins!");   // doesn't re-render yet
                            // → React re-renders ONCE here, all updates applied
}
This is automatic in React 18+ everywhere — including inside setTimeout and promises. In React 17 and below, batching only happened inside React event handlers.

Confirmation Before Destructive Actions

Two ways to confirm before deleting

window.confirm is the zero-code option. A custom modal gives you full control over styling and UX, and is what interviewers expect in a UI build.

// 1. window.confirm — native browser dialog, instant
function removeTask(id) {
  if (window.confirm("Delete this task?")) {
    setTasks(tasks.filter(t => t.id !== id));
  }
}

// 2. Custom modal — store which task is pending deletion
const [pendingDeleteId, setPendingDeleteId] = useState(null);

// delete button just opens the modal
<button onClick={() => setPendingDeleteId(task.id)}>Delete</button>

// modal renders conditionally
{pendingDeleteId !== null && (
  <div className="modal-overlay" onClick={() => setPendingDeleteId(null)}>
    <div className="modal" onClick={(e) => e.stopPropagation()}>
      <p>Delete this task?</p>
      <button onClick={() => {
        setTasks(tasks.filter(t => t.id !== pendingDeleteId));
        setPendingDeleteId(null);
      }}>Confirm</button>
      <button onClick={() => setPendingDeleteId(null)}>Cancel</button>
    </div>
  </div>
)}
stopPropagation: clicking inside the modal box would bubble up to the overlay and close it. e.stopPropagation() on the inner div prevents that.
Two divs, not one: the overlay handles full-screen dimming and click-outside-to-close. The modal is just the small centered box. Separating them keeps styling clean and makes stopPropagation work correctly.

Never mutate state directly — always create a new array

// ✗ mutates in place — React won't detect change, no re-render
board[row][col] = "X";

// ✓ create a new 2D array
const alteredBoard = board.map((r, rIdx) =>
  r.map((cell, cIdx) => rIdx === row && cIdx === col ? "X" : cell)
);
setBoard(alteredBoard);
stateimmutabilityhigh priority

Derive values from state instead of storing them as state

If a value can be computed from existing state, don't make it state. Over-stating causes sync bugs and more reset logic.

// ✗ storing derived values as state — gets out of sync with board
const [winner, setWinner] = useState(null);
const [draw, setDraw] = useState(false);

// ✓ derive them fresh every render from board
const winner = gameHasWinner(board, "X") ? "Player X"
             : gameHasWinner(board, "O") ? "Player O"
             : null;
const draw = !winner && noAvailableCells(board);
const isGameOver = winner !== null || draw;
Minimal state = just board, isXTurn, isComputerThinking. Everything else follows from the board.

Props are a single object — destructure with {}

// ✗ wrong — value is the whole props object, rest are undefined
const CellButton = (value, hoveredValue, onClick) => { ... }

// ✓ correct — destructure the props object
const CellButton = ({ value, hoveredValue, onClick }) => {

Object {} vs array [] destructuring

// object — matches by NAME
const { value, hoveredValue } = props;

// array — matches by POSITION, name it whatever you want
const [board, setBoard] = useState(...);
const [isXTurn, setIsXTurn] = useState(...);
useState returns a tuple so you can name state and setter whatever makes sense. If it returned an object you'd have to write const {'{'} state: board, setState: setBoard {'}'} every time.

setTimeout is async — put follow-up code inside the callback

// ✗ setIsComputerThinking runs immediately, not after delay
setTimeout(randomThinkingInterval);
setIsComputerThinking(false);

// ✓ everything after the delay goes inside the callback
timeoutId.current = setTimeout(() => {
  setIsComputerThinking(false);
  updateCell(random.row, random.col);
}, randomThinkingInterval);
Store the timeout id in a useRef so you can clearTimeout(timeoutId.current) on reset — otherwise the callback fires on the fresh board.

Rules of Hooks — hooks only in function components, not regular functions

// ✗ calling useState inside a helper function called in .map() — React error
const renderedCell = (value, rowIdx, colIdx) => {
  const [isHovered, setIsHovered] = useState(false); // INVALID
};

// ✓ extract as a proper React component with capital letter
const CellButton = ({ value, onClick }) => {
  const [isHovered, setIsHovered] = useState(false); // valid
  return <button onClick={onClick}>{value}</button>;

flatMap — map + flat in one step

Returning [item] includes it, returning [] skips it. Useful for filter+map on nested arrays in one pass.

// get all empty cells from a 2D board
const availableCells = board.flatMap((row, rowIdx) =>
  row.flatMap((cell, colIdx) =>
    cell === "_" ? [{ row: rowIdx, col: colIdx }] : []
  )
);
In practice .filter().map() is more readable. Reach for flatMap when you're already working with nested arrays.

React — Controlled Inputs & Re-renders

Controlled input — value + onChange are required together

A controlled input means React owns the value via state. Without onChange, the input is read-only and React warns you.

// controlled — React owns the value
const [celsius, setCelsius] = useState("");

<input
  type="number"        // not "string" — "string" isn't a valid type
  value={celsius}      // curly braces, not quotes — quotes = literal string
  onChange={(e) => setCelsius(e.target.value)}
/>
<input /> is self-closing because input is a void element — it can never have children. Same for <br />, <img />. In JSX you must use />.
inputFor is wrong — React renames it to htmlFor. The HTML attribute for is a reserved word in JS, so React uses htmlFor instead.
React controlled input JSX

Re-renders — every setState call triggers one

Every useState setter re-runs the component function top to bottom. So every keystroke → setCelsius() → re-render. Anything defined inside the component is recreated on each render.

// define debounce outside the component, wrap with useCallback inside
function debounce(fn, delay) {
  let timeoutId;
  return (...args) => {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => fn(...args), delay);
  };
}

function App() {
  const debouncedFn = useCallback(
    debounce(myFn, 300),
    [] // [] = only create once on mount
  );
}
useState setters are guaranteed stable by React — they never change between renders. This is why a stale closure from [] still works correctly here.
re-render useCallback debounce
React — IDs, State & List Rendering

A plain let counter resets on every render — use state or a ref

React re-runs the whole component function on every render. A plain variable inside the component is recreated each time, so let counter = 0 resets to 0 on every re-render → every task gets the same id.

// 1. useRef — best for a counter (doesn't trigger a re-render)
const idRef = useRef(0);
function addTask(summary) {
  setTasks([...tasks, { summary, id: idRef.current }]);
  idRef.current++;
}

// 2. Date.now() — fine for click-driven demos
id: Date.now()

// 3. crypto.randomUUID() — cleanest, no setup
id: crypto.randomUUID()
Duplicate ids break two things: tasks.filter(t => t.id !== deletedId) deletes every matching task at once, and React's key={'{'}task.id{'}'} loses track of which row is which.
useRef Date.now crypto.randomUUID

Render an array with .map() — the standard React pattern

.map() returns a new array of JSX elements, one per item, and React renders that array. Not forEach (returns nothing).

<ul>
  {'{'}tasks.map((task) => (
    <li key={'{'}task.id{'}'}>
      <span>{'{'}task.summary{'}'}</span>
      <button onClick={'{'}() => removeTask(task.id){'}'}>Delete</button>
    </li>
  )){'}'}
</ul>
Blank list? Curly braces after the arrow are a function body, not an implicit return. (task) => {'{
  • ...
    • }'}     with no return gives undefined for every item. Use parentheses (task) => ( ... ) for implicit return.

    HTML — Lists (<ul>, <ol>, <li>)

    <ul> / <ol> are the container, <li> is each row

    <li> must be a direct child of <ul> or <ol>. Use <ul> when order is irrelevant, <ol> for steps or rankings.

    <ul>
  <li>Buy milk</li>
  <li>Walk dog</li>
</ul>
    Wrapping each <li> in a <div> is invalid HTML. The <ul> is already the grouping container. Interviewers notice.

    Bullets vanish when you put display: flex on the <li>

    The bullet marker comes from the list-item display type. Setting display: flex replaces it. Move flex to an inner wrapper instead.

    // keeps bullets — flex on inner div, li stays semantic
<li key={'{'}task.id{'}'}>
  <div style={'{{'} display: "flex", gap: "4px" {'}}'}>
    <span>{'{'}task.summary{'}'}</span>
    <button onClick={'{'}() => removeTask(task.id){'}'}>Delete</button>
  </div>
</li>

    Debounce & Throttle

    debounce — wait until the user stops

    Fires the function only after N ms of silence. Every new call resets the timer. Use for search inputs, autocomplete, form validation.

    // debounce(fn, delayMs) — fires fn only after 300ms of no new calls
const debouncedSearch = debounce((query) => {
  fetchResults(query);
}, 300);

searchInput.addEventListener('input', (e) => {
  debouncedSearch(e.target.value);
});
    The debouncedSearch variable holds a closure — one shared timeoutId across all calls. Every keystroke cancels the previous timer and starts a new one.
    debounce search bar high priority

    throttle — fire at most once per N ms

    Doesn't wait for silence — fires immediately, then ignores calls until the delay has passed. Use for scroll handlers, resize, mousemove.

    Use debounce when

    • Search / autocomplete inputs
    • Form field validation
    • Window resize

    Use throttle when

    • Scroll position tracking
    • Mouse move / drag
    • Rate-limiting button clicks
    throttle scroll
    Array.prototype.reduce

    Collapses an array to one value — number, object, Map, anything

    // reduce(callbackFn, initialValue)
// callback args: (accumulator, currentItem) — must return accumulator
const sum = [1,2,3,4].reduce((acc, item) => acc + item, 0);  // 10

// frequency map
const freq = fruits.reduce((acc, item) => {
  acc[item] = (acc[item] ?? 0) + 1;
  return acc;
}, {});

// build a Map — Map is "one value"
const byId = vehicles.reduce((acc, v) => {
  acc.set(v.id, v);
  return acc;
}, new Map());
    Always return acc inside the callback. Forgetting it means the next step gets undefined.
    array functional high priority
    map, filter, reduce — callback signatures

    All three pass (value, index, array) to their callback

    // map — must return transformed value, same-length output
vehicles.map(v => v.id);

// filter — must return boolean, shorter or equal output
vehicles.filter(v => v.stationarySeconds > 300);

// chaining — filter first (smaller array), then sort, then map
const result = vehicles
  .filter(v => v.stationarySeconds > 300)
  .sort((a, b) => b.stationarySeconds - a.stationarySeconds)
  .map(v => v.id);

// _ convention — "I don't care about this parameter"
arr.map((_, index) => index * 2);
    map filter high priority
    for...of vs for...in

    Always use for...of. Avoid for...in on arrays.

    for...of iterates values. for...in iterates keys — on arrays those keys are string indices ("0", "1"…).

    for (const x of arr) console.log(x);   // 10, 20, 30 ✓
for (const i in arr) console.log(i);   // "0", "1", "2" — strings ✗

// for plain objects — use Object.keys/values/entries
for (const [key, value] of Object.entries(freq)) { ... }

// for Map — for...of directly
for (const [key, value] of myMap) { ... }
    iteration gotcha
    Plain object {} vs Map

    Which one to reach for

    Plain object {}

    • Simpler syntax
    • Fine for string/number keys
    • Bracket notation: obj[key]

    Map

    • Keys can be anything (objects, arrays)
    • Numbers stay numbers — no coercion
    • .size built in
    • Must use .get(key)
    Interview default: plain object {} for string keys (chars, words). Reach for Map when keys are numbers you need to preserve, or for adjacency lists.
    // plain object — keys always coerced to strings
obj[1] === obj["1"];  // true — same key ✗

// Map — numbers stay numbers
mp.get(1) !== mp.get("1");  // true — different keys ✓
