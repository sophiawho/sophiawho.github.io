React — Forms

Wrap inputs in a <form> so Enter key submits

A <form> with onSubmit handles both button clicks and Enter key — no extra keydown listener needed. The form wraps all related inputs as children; each input still manages its own state independently.

// wrap inputs in a form — Enter OR button click both trigger onSubmit
<form onSubmit={(e) => {
  e.preventDefault();   // required — prevents full page reload
  handleSubmit();
}}>
  <input value={name} onChange={(e) => setName(e.target.value)} placeholder="Name" />
  <input value={email} onChange={(e) => setEmail(e.target.value)} placeholder="Email" />
  <textarea value={notes} onChange={(e) => setNotes(e.target.value)} />
  <button type="submit">Submit</button>
</form>
e.preventDefault() is required. Without it the form triggers a full page reload on submit — the browser's default behavior for forms.
button type matters: type="submit" triggers onSubmit. A button with type="button" inside the form does NOT. The default type for a button inside a form is submit, so you can omit it — but being explicit is clearer.

React — Controlled Inputs & Re-renders

Controlled input — value + onChange are required together

A controlled input means React owns the value via state. Without onChange, the input is read-only and React warns you.

// controlled — React owns the value
const [celsius, setCelsius] = useState("");

<input
  type="number"        // not "string" — "string" isn't a valid type
  value={celsius}      // curly braces, not quotes — quotes = literal string
  onChange={(e) => setCelsius(e.target.value)}
/>
<input /> is self-closing because input is a void element — it can never have children. Same for <br />, <img />. In JSX you must use />.
inputFor is wrong — React renames it to htmlFor. The HTML attribute for is a reserved word in JS, so React uses htmlFor instead.
React controlled input JSX

Re-renders — every setState call triggers one

Every useState setter re-runs the component function top to bottom. So every keystroke → setCelsius() → re-render. Anything defined inside the component is recreated on each render.

// define debounce outside the component, wrap with useCallback inside
function debounce(fn, delay) {
  let timeoutId;
  return (...args) => {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => fn(...args), delay);
  };
}

function App() {
  const debouncedFn = useCallback(
    debounce(myFn, 300),
    [] // [] = only create once on mount
  );
}
useState setters are guaranteed stable by React — they never change between renders. This is why a stale closure from [] still works correctly here.

React — IDs, State & List Rendering

A plain let counter resets on every render — use state or a ref

React re-runs the whole component function on every render. A plain variable inside the component is recreated each time, so let counter = 0 resets to 0 on every re-render → every task gets the same id.

// 1. useRef — best for a counter (doesn't trigger a re-render)
const idRef = useRef(0);
function addTask(summary) {
  setTasks([...tasks, { summary, id: idRef.current }]);
  idRef.current++;
}

// 2. Date.now() — fine for click-driven demos
id: Date.now()

// 3. crypto.randomUUID() — cleanest, no setup
id: crypto.randomUUID()
Duplicate ids break two things: tasks.filter(t => t.id !== deletedId) deletes every matching task at once, and React's key={'{'}task.id{'}'} loses track of which row is which.
useRef Date.now crypto.randomUUID

Render an array with .map() — the standard React pattern

.map() returns a new array of JSX elements, one per item, and React renders that array. Not forEach (returns nothing).

<ul>
  {'{'}tasks.map((task) => (
    <li key={'{'}task.id{'}'}>
      <span>{'{'}task.summary{'}'}</span>
      <button onClick={'{'}() => removeTask(task.id){'}'}>Delete</button>
    </li>
  )){'}'}
</ul>
Blank list? Curly braces after the arrow are a function body, not an implicit return. (task) => {'{
  • ...
    • }'}     with no return gives undefined for every item. Use parentheses (task) => ( ... ) for implicit return.

    HTML — Lists (<ul>, <ol>, <li>)

    <ul> / <ol> are the container, <li> is each row

    <li> must be a direct child of <ul> or <ol>. Use <ul> when order is irrelevant, <ol> for steps or rankings.

    <ul>
  <li>Buy milk</li>
  <li>Walk dog</li>
</ul>
    Wrapping each <li> in a <div> is invalid HTML. The <ul> is already the grouping container. Interviewers notice.

    Bullets vanish when you put display: flex on the <li>

    The bullet marker comes from the list-item display type. Setting display: flex replaces it. Move flex to an inner wrapper instead.

    // keeps bullets — flex on inner div, li stays semantic
<li key={'{'}task.id{'}'}>
  <div style={'{{'} display: "flex", gap: "4px" {'}}'}>
    <span>{'{'}task.summary{'}'}</span>
    <button onClick={'{'}() => removeTask(task.id){'}'}>Delete</button>
  </div>
</li>

    The JavaScript Event Loop

    Call stack → Web APIs → Event queue → Event loop

    JS is single-threaded. Promises (microtasks) drain before setTimeout callbacks (event queue), even with 0ms delay.

    Debounce & Throttle

    debounce — wait until the user stops

    Fires the function only after N ms of silence. Every new call resets the timer. Use for search inputs, autocomplete, form validation.

    // debounce(fn, delayMs) — fires fn only after 300ms of no new calls
const debouncedSearch = debounce((query) => {
  fetchResults(query);
}, 300);

searchInput.addEventListener('input', (e) => {
  debouncedSearch(e.target.value);
});
    The debouncedSearch variable holds a closure — one shared timeoutId across all calls. Every keystroke cancels the previous timer and starts a new one.
    debounce search bar high priority

    throttle — fire at most once per N ms

    Doesn't wait for silence — fires immediately, then ignores calls until the delay has passed. Use for scroll handlers, resize, mousemove.

    Use debounce when

    • Search / autocomplete inputs
    • Form field validation
    • Window resize

    Use throttle when

    • Scroll position tracking
    • Mouse move / drag
    • Rate-limiting button clicks
    throttle scroll
    Array.prototype.reduce

    Collapses an array to one value — number, object, Map, anything

    // reduce(callbackFn, initialValue)
// callback args: (accumulator, currentItem) — must return accumulator
const sum = [1,2,3,4].reduce((acc, item) => acc + item, 0);  // 10

// frequency map
const freq = fruits.reduce((acc, item) => {
  acc[item] = (acc[item] ?? 0) + 1;
  return acc;
}, {});

// build a Map — Map is "one value"
const byId = vehicles.reduce((acc, v) => {
  acc.set(v.id, v);
  return acc;
}, new Map());
    Always return acc inside the callback. Forgetting it means the next step gets undefined.
    array functional high priority
    map, filter, reduce — callback signatures

    All three pass (value, index, array) to their callback

    // map — must return transformed value, same-length output
vehicles.map(v => v.id);

// filter — must return boolean, shorter or equal output
vehicles.filter(v => v.stationarySeconds > 300);

// chaining — filter first (smaller array), then sort, then map
const result = vehicles
  .filter(v => v.stationarySeconds > 300)
  .sort((a, b) => b.stationarySeconds - a.stationarySeconds)
  .map(v => v.id);

// _ convention — "I don't care about this parameter"
arr.map((_, index) => index * 2);
    map filter high priority
    for...of vs for...in

    Always use for...of. Avoid for...in on arrays.

    for...of iterates values. for...in iterates keys — on arrays those keys are string indices ("0", "1"…).

    for (const x of arr) console.log(x);   // 10, 20, 30 ✓
for (const i in arr) console.log(i);   // "0", "1", "2" — strings ✗

// for plain objects — use Object.keys/values/entries
for (const [key, value] of Object.entries(freq)) { ... }

// for Map — for...of directly
for (const [key, value] of myMap) { ... }
    iteration gotcha
    Plain object {} vs Map

    Which one to reach for

    Plain object {}

    • Simpler syntax
    • Fine for string/number keys
    • Bracket notation: obj[key]

    Map

    • Keys can be anything (objects, arrays)
    • Numbers stay numbers — no coercion
    • .size built in
    • Must use .get(key)
    Interview default: plain object {} for string keys (chars, words). Reach for Map when keys are numbers you need to preserve, or for adjacency lists.
    // plain object — keys always coerced to strings
obj[1] === obj["1"];  // true — same key ✗

// Map — numbers stay numbers
mp.get(1) !== mp.get("1");  // true — different keys ✓
