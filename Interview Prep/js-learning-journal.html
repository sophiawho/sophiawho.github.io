React — Controlled Inputs & Re-renders

Controlled input — value + onChange are required together

A controlled input means React owns the value via state. Without onChange, the input is read-only and React warns you.

// controlled — React owns the value
const [celsius, setCelsius] = useState("");

<input
  type="number"        // not "string" — "string" isn't a valid type
  value={celsius}      // curly braces, not quotes — quotes = literal string
  onChange={(e) => setCelsius(e.target.value)}
/>
<input /> is self-closing because input is a void element — it can never have children. Same for <br />, <img />. In JSX you must use />.
inputFor is wrong — React renames it to htmlFor. The HTML attribute for is a reserved word in JS, so React uses htmlFor instead.
React controlled input JSX

Re-renders — every setState call triggers one

Every useState setter re-runs the component function top to bottom. So every keystroke → setCelsius() → re-render. Anything defined inside the component is recreated on each render.

// GOOD — useCallback with empty dependency array, debounce defined outside
function debounce(fn, delay) { // pure utility, define outside component
  let timeoutId;
  return (...args) => {
    clearTimeout(timeoutId);
    timeoutId = setTimeout(() => fn(...args), delay);
  };
}

function App() {
  const debouncedFn = useCallback(
    debounce(myFn, 300),
    [] // [] = only create once on mount
  );
}
useState setters (setCelsius, etc.) are guaranteed stable by React — they never change between renders. This is why a stale closure from [] still works correctly here.

TypeScript — Enums & Types

TypeScript is JavaScript + types/enums/interfaces

Everything valid in JS is valid in TS. It compiles down to plain JS. In CoderPad and GFE you can pick TypeScript from the language dropdown.

// TS enum — preferred over Object.freeze in TypeScript
enum InputType {
  CELSIUS = "celsius",
  FAHRENHEIT = "fahrenheit",
}

// JS equivalent with Object.freeze (when TS isn't available)
const InputType = Object.freeze({
  CELSIUS: "celsius",
  FAHRENHEIT: "fahrenheit",
});

// usage — same either way
convertTemperature(e.target.value, InputType.CELSIUS);

// TS function signature
function convertTemperature(value: string, fromUnit: InputType): void { ... }
Object.freeze prevents mutation — trying to reassign a property silently fails (or throws in strict mode). It's the JS idiom for constants that should never change.

The JavaScript Event Loop

Call stack → Web APIs → Event queue → Event loop

JS is single-threaded. The event loop coordinates what runs and when.

// Execution order
setTimeout(() => console.log('timeout'), 0);
Promise.resolve().then(() => console.log('promise'));
console.log('sync');

// Output:
// sync       ← call stack runs first
// promise    ← microtask queue (Promises) drains before event queue
// timeout    ← event queue, even with 0ms delay
Call stack — where JS runs now, one function at a time.
Web APIs — browser handles setTimeout, fetch, DOM events outside JS.
Microtask queue — Promises go here; drained completely after each task.
Event queue — setTimeout callbacks wait here until stack is empty.
Event loop — checks "is stack empty? pull next from queue."
setTimeout(fn, 0) doesn't mean "run immediately" — it means "run after current stack + all microtasks are done, at the earliest."

Debounce, Throttle & Lodash

debounce — wait until the user stops

Not native to JS — comes from lodash (or write the polyfill). Fires the function only after N ms of silence. Every new call resets the timer. Use for search inputs, autocomplete, form validation.

// import (not native — needs lodash)
import { debounce, throttle } from 'lodash';
// CDN: <script src="https://cdn.jsdelivr.net/npm/lodash@4/lodash.min.js"></script>

// debounce(fn, delayMs) — fires fn only after 300ms of no new calls
const debouncedSearch = debounce((query) => {
  fetchResults(query);
}, 300);

searchInput.addEventListener('input', (e) => {
  debouncedSearch(e.target.value);
});
The debouncedSearch variable holds a closure — one shared timeoutId across all calls. Every keystroke cancels the previous timer and starts a new one. When the user stops, the last timer fires.
debounce search bar high priority

throttle — fire at most once per N ms

Unlike debounce, throttle doesn't wait for silence — it fires immediately, then ignores calls until the delay has passed. Use for scroll handlers, resize, mousemove.

// throttle(fn, limitMs)
// fires at most once every 200ms no matter how often scroll fires
const throttledScroll = throttle(() => {
  updateScrollPosition();
}, 200);

window.addEventListener('scroll', throttledScroll);

// debounce on scroll = only fires AFTER user stops scrolling (bad UX)
// throttle on scroll = fires steadily while scrolling (good UX)

Use debounce when

  • Search / autocomplete inputs
  • Form field validation
  • Window resize (recalculate layout after done)

Use throttle when

  • Scroll position tracking
  • Mouse move / drag
  • Rate-limiting button clicks

Array.prototype.reduce

What reduce does

Collapses an array down to one value. That value can be a number, string, object, or Map — anything. Unlike map (same length) or filter (shorter), reduce always returns a single thing.

Think of a cashier tallying a receipt: starts at $0, adds each item one by one, hands you one number at the end.

// reduce(callbackFn, initialValue)
// Two levels:
//   outer — reduce's own two args: the callback function + starting value
//   inner — callback's own args:   accumulator + currentItem

const result = array.reduce((accumulator, currentItem) => {
  // update accumulator using currentItem
  return accumulator;  // ALWAYS return it, or next step gets undefined
}, startingValue);

// one-liner: arrow function with no braces = implicit return
const sum = [1,2,3,4].reduce((accumulator, item) => accumulator + item, 0);
// step by step: 0+1=1 → 1+2=3 → 3+3=6 → 6+4=10
array functional high priority

reduce to build a frequency map (plain object)

One of the most common interview patterns. The accumulator starts as {} and gets built up key by key.

const fruits = ['apple', 'banana', 'apple', 'orange', 'banana', 'apple'];

const freq = fruits.reduce((accumulator, item) => {
  accumulator[item] = (accumulator[item] ?? 0) + 1;
  return accumulator;  // must return or next step gets undefined
}, {});

// { apple: 3, banana: 2, orange: 1 }
The accumulator starts as {} so the result is a plain object. Start with new Map() and use .set() instead if you need Map features.

reduce to build a Map — Map is technically "one value"

Map is a single object, so reduce is the right tool. Great for O(1) lookups by ID.

const byId = vehicles.reduce((accumulator, vehicle) => {
  accumulator.set(vehicle.id, vehicle);
  return accumulator;
}, new Map());

byId.get('v1');  // { id: 'v1', status: 'stopped' }
map, filter, reduce — callback signatures

All three pass (value, index, array) to their callback

The third argument — the original array — is almost never used. In practice just use (item) or (item, index). Use _ to signal "intentionally unused."

// map(callback) — must return transformed value, same length output
array.map((currentItem, index) => { return /* new value */; });
vehicles.map(vehicle => vehicle.id);  // one-liner, implicit return

// filter(callback) — must return true/false, shorter or equal output
array.filter((currentItem, index) => { return /* boolean */; });
vehicles.filter(v => v.stationarySeconds > 300);

// third arg exists but almost never needed
arr.filter((item, index, array) => array.indexOf(item) === index); // dedup

// _ convention — "I don't care about this parameter"
arr.findIndex((_, i) => Object.hasOwn(arr, i));
The original array is passed as a convenience in case you need to look back at the full array mid-callback. In practice new Set(arr) or other methods handle those edge cases more cleanly.
for...of vs for...in

Always use for...of. Avoid for...in on arrays.

for...of iterates values. for...in iterates keys — and on arrays those keys are string indices ("0", "1"…), which is almost never what you want.

const arr = [10, 20, 30];

for (const x of arr) console.log(x);   // 10, 20, 30  ← values ✓
for (const i in arr) console.log(i);   // "0", "1", "2" ← string keys ✗

// for plain objects: Object.keys() preferred over for...in
// (avoids inherited prototype keys)
for (const key of Object.keys(freq))            { ... }  // keys only ✓
for (const value of Object.values(freq))        { ... }  // values only
for (const [key, value] of Object.entries(freq)){ ... }  // both

// for Map — just use for...of directly
for (const [key, value] of myMap) { ... }
Gotcha: for...in on objects works but can pick up inherited prototype keys. Object.keys() only returns the object's own keys — safer habit.
iteration gotcha
Plain object {} vs Map for frequency counting

Which one to reach for

Plain object {}

  • Simpler syntax, less to type
  • Fine for string/number keys
  • Bracket notation works: obj[key]

Map

  • Keys can be anything (objects, arrays)
  • Numbers stay numbers — no coercion
  • .size built in (no Object.keys().length)
  • Must use .get(key) — no bracket notation
Interview default: plain object {} for string keys (chars, words). Reach for Map when keys are numbers you need to preserve, or when building an adjacency list.
// plain object — keys always coerced to strings
const obj = {};
obj[1] === obj["1"];  // true — same key ✗

// Map — numbers stay numbers
const mp = new Map();
mp.set(1, 'a');
mp.get(1) !== mp.get("1");  // true — different keys ✓
Function.prototype.call

call() sets what this is inside a function

Every function has a .call() method. The first argument is thisArg — what this refers to inside the function. The rest are normal arguments.

fn.call(thisArg, arg1, arg2, ...)
//      ↑ sets `this`  ↑ normal args start here

// easy trap in a polyfill:
callbackFn.call(acc, curVal, i, this)
// ↑ this sets acc as `this` inside the callback
//   curVal becomes the FIRST arg, not acc!
//   the accumulator is never passed as a parameter

// correct:
callbackFn(acc, curVal, i, this)           // just call it directly ✓
callbackFn.call(undefined, acc, curVal, i, this)  // explicit thisArg ✓
Waymo relevance: low. Comes up in polyfill questions (implement bind, debounce with this preservation). File away — don't need to nail it for the TPS.
polyfills low priority for Waymo
Detecting optional parameters — arguments.length

Use arguments.length to tell if a param was actually passed

Checking initialValue !== undefined fails if someone explicitly passes undefined. arguments.length counts what was actually passed — even if the value is undefined.

// ✗ breaks when called with myReduce(cb, undefined)
if (initialValue !== undefined) { ... }

// ✓ correct — arguments is a special object inside regular functions
if (arguments.length >= 2) {
  acc = initialValue;   // initialValue was explicitly provided
} else {
  acc = this[0];        // no initialValue — use first element
  startIndex = 1;
}
arguments is only available in regular function declarations — not arrow functions. Arrow functions inherit arguments from their enclosing scope.
findIndex and the _ convention

findIndex returns -1 if nothing matches — useful as a guard

Cleaner than a while loop + separate length check. Returns the index of the first element where the callback returns true, or -1.

// find first non-sparse index in an array (for myReduce polyfill)
startIndex = this.findIndex((_, i) => Object.hasOwn(this, i));
if (startIndex === -1) throw new TypeError('Reduce of empty array with no initial value');
acc = this[startIndex];
startIndex += 1;

// _ = "intentionally unused" — just the value, I only need the index
// same pattern works in map, filter, reduce, forEach
arr.findIndex((_, index) => index > 2);
arr.map((_, index) => index * 2);  // array of doubled indices
findIndex convention
What is a polyfill?

Reimplementing a built-in from scratch

A polyfill recreates a native method — either to deeply understand how it works, or to support older browsers that don't have it. GFE has a whole track of these: implement debounce, Promise.all, Array.prototype.map, Function.prototype.call, etc.

// the real built-in
[1, 2, 3].reduce((acc, x) => acc + x, 0);

// a polyfill — you implementing reduce yourself
Array.prototype.myReduce = function(callbackFn, initialValue) {
  let acc;
  let startIndex;

  if (arguments.length >= 2) {
    acc = initialValue;
    startIndex = 0;
  } else {
    startIndex = this.findIndex((_, i) => Object.hasOwn(this, i));
    if (startIndex === -1) throw new TypeError('Empty array with no initial value');
    acc = this[startIndex++];
  }

  for (let i = startIndex; i < this.length; i++) {
    if (Object.hasOwn(this, i)) {
      acc = callbackFn(acc, this[i], i, this);
    }
  }
  return acc;
};
Waymo relevance: low. Polyfills test deep JS knowledge but the TPS is focused on UI builds and fleet data manipulation. Good for GFE practice, not a priority right now.
polyfills low priority for Waymo
